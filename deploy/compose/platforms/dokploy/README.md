# Ethora Core on Dokploy

[Dokploy](https://dokploy.com) is a self-hosted PaaS with its own reverse
proxy (Traefik). Ethora Core runs on it in two ways, both from the compose
bundle in this directory's grandparent (`deploy/compose`):

1. **A Compose service from the public installer repository**
   (`github.com/dappros/ethora-install`, compose path
   `deploy/compose/docker-compose.yml`). Dokploy clones the repository and
   runs `docker compose` from the compose file's directory, so the bundle's
   `./scripts` and `./templates` bind mounts resolve from the checkout. This
   is the supported way; the steps below were run end to end on Dokploy
   v0.30.8 and the bundle's `verify` check passed through Dokploy's proxy.
2. **The template in this directory** (`docker-compose.yml`, `template.toml`,
   `meta.json`, `ethora.svg`), in the format of
   [github.com/Dokploy/templates](https://github.com/Dokploy/templates): the
   same compose file without the bundled proxy, the scripts and templates
   carried as file mounts, every secret generated by Dokploy. Deployed and
   verified end to end from a locally served catalogue on the same Dokploy
   version; not yet in Dokploy's catalogue (see "Submit the template").

Either way the bundled Caddy stays off (Dokploy's Traefik terminates TLS and
routes the five hosts), the data lives in Docker volumes prefixed with the
service's app name, and the installed stack is the one described in
`../../README.md`.

Server: 2 vCPU and 4 GB RAM for Ethora Core on top of what Dokploy needs
itself (about 2 GB with its Postgres, Redis and Traefik); 8 GB in total is
comfortable. Dokploy itself: `curl -sSL https://dokploy.com/install.sh | sh`
on a clean Ubuntu host, then register the first user on `http://<host>:3000`.

## DNS

Point the five hosts at the Dokploy server before deploying, all plain A
records (a wildcard `*.chat.example.com` covers them):

| Host | Routed to |
|---|---|
| `api.chat.example.com` | `api:8080` |
| `app.chat.example.com` | `frontend:8080`; `centrifugo:8000` for `/connection/websocket` |
| `xmpp.chat.example.com` | `xmpp:5280`, paths `/ws` and `/bosh` only |
| `files.chat.example.com` | `minio:9000` |
| `secure-files.chat.example.com` | `api:8080` (chat attachments, gated by chat membership; the API serves this host itself) |

`chat.example.com` is the root domain; every host derives from it. For a
test without DNS use `<server IP with dashes>.sslip.io` as the root. With
the Enterprise `ai` module (`COMPOSE_PROFILES=ai` in the environment, a
licence key and `docker login` for the private image; see the bundle's
README, "Enterprise modules") add a sixth host, `widget.chat.example.com`,
routed to `widget:8080`; the other modules need `playground.` to
`playground:3020`, `mcp.` to `mcp:3030`, `uptime.` to `uptime:8099` behind a
basic-auth middleware, and `api.<root>/push/` to `push:8098` with the
prefix stripped.

## Way 1: Compose service from git (supported)

In Dokploy: project > **Create Service** > **Compose**.

1. **Provider**: Git, repository URL `https://github.com/dappros/ethora-install`,
   branch `main` (or a release line such as `2610`), compose path
   `deploy/compose/docker-compose.yml`. No SSH key is needed for a public
   HTTPS URL. Turn **Isolated Deployment** on (Advanced). Without it every
   routed service joins Dokploy's shared `dokploy-network` under its compose
   service name, and any other compose service on the same Dokploy with a
   service called `api`, `xmpp`, `minio`, `frontend` or `centrifugo` (a
   second Ethora stack included) is resolved by that name too: on a host
   with two stacks the second one's API reached the first one's MinIO
   (access key rejected), ejabberd (403) and API (`init` failed on a
   duplicate base app). With it the stack gets its own network, named
   after the app, that Traefik joins. Both settings were run; a single
   stack works either way, two stacks only with isolation.
2. **Environment**: paste the bundle's `.env.example` with every value set:
   `ROOT_DOMAIN`, `ADMIN_EMAIL`, a random value of 32+ letters and digits for
   every secret, and an empty `COMPOSE_PROFILES` (no bundled Caddy). On any
   machine with bash, `./configure.sh --no-caddy --domain chat.example.com
   --admin-email you@example.com --out /tmp/ethora.env` writes a complete
   file to paste. Keep "Create .env file" on (the default): Dokploy writes
   the variables to `.env` next to the compose file, which is where the
   bundle reads them. The per-host overrides `API_DOMAIN`, `WEB_DOMAIN`,
   `XMPP_DOMAIN`, `FILES_DOMAIN` may stay empty: Dokploy passes the file to
   `docker compose` as is, so the compose defaults (`api.<ROOT_DOMAIN>`, ...)
   apply.
3. **Domains**, one per routed service, each with HTTPS on and certificate
   **Let's Encrypt**:

   | Service | Host | Port | Path |
   |---|---|---|---|
   | `api` | `api.chat.example.com` | 8080 | `/` |
   | `frontend` | `app.chat.example.com` | 8080 | `/` |
   | `centrifugo` | `app.chat.example.com` | 8000 | `/connection/websocket` |
   | `xmpp` | `xmpp.chat.example.com` | 5280 | `/ws` |
   | `xmpp` | `xmpp.chat.example.com` | 5280 | `/bosh` |
   | `minio` | `files.chat.example.com` | 9000 | `/` |
   | `api` | `secure-files.chat.example.com` | 8080 | `/` |

   Leave "Strip Path" off (the default), so `/ws`, `/bosh` and
   `/connection/websocket` reach the containers. Traefik gives the longer
   path rule priority, so `/connection/websocket` reaches centrifugo and
   everything else on `app.` reaches the frontend; on `xmpp.` only `/ws` and
   `/bosh` are routed, which keeps ejabberd's `/api` and `/admin` internal.
4. **Deploy**. Dokploy clones the repository to
   `/etc/dokploy/compose/<app name>/code`, adds the Traefik labels and the
   `dokploy-network` to the routed services, and runs `docker compose -p
   <app name> -f deploy/compose/docker-compose.yml up -d`. The first
   deployment pulls the images (about 4 GB on disk) and takes a few minutes;
   the deployment log ends with `Docker Compose Deployed` once `init` has
   started, and `init`'s own log (Logs tab, or `docker logs <app
   name>-init-1`) ends with `done`. Certificates are requested by Traefik as
   soon as each container is healthy.

Then open `https://app.chat.example.com` and sign in with `ADMIN_EMAIL` and
`ADMIN_PASSWORD`.

The compose file is rewritten by Dokploy before every deployment (parsed and
serialised again to add the labels); the bundle's YAML anchors and merge
keys survive this, and `config`, `mongo-init` and `init` stay one-shot
containers that exit with 0.

### The same with the API

Create a key under Settings > Profile > API/CLI. A key has a rate limit of
10 requests per 24 hours by default, which the steps below exceed: turn the
rate limit off when creating it (`rateLimitEnabled: false` in the API,
`user.createApiKey`). Every endpoint is `POST /api/<router>.<procedure>`
with a JSON body (`GET` with query parameters for reads), header
`x-api-key`; the OpenAPI document is at
`/api/settings.getOpenApiDocument` and Swagger UI at `/swagger`.

```bash
DOKPLOY=http://dokploy.example.com:3000; KEY=...; R=chat.example.com
api() { curl -sS -X "$1" -H "x-api-key: $KEY" -H 'Content-Type: application/json' "$DOKPLOY/api/$2" "${@:3}"; }

# project (returns {"project":{...},"environment":{...}}; the default environment is "production")
api POST project.create -d '{"name":"ethora","description":"Ethora Core"}'
# compose service from git
api POST compose.create -d '{"name":"ethora-core","environmentId":"<environmentId>","composeType":"docker-compose","sourceType":"git"}'
api POST compose.update -d '{"composeId":"<composeId>","sourceType":"git","customGitUrl":"https://github.com/dappros/ethora-install","customGitBranch":"main","composePath":"deploy/compose/docker-compose.yml","createEnvFile":true,"isolatedDeployment":true}'
# environment: the .env content as one string
python3 -c 'import json,sys; print(json.dumps({"composeId": sys.argv[1], "env": open(sys.argv[2]).read(), "createEnvFile": True}))' <composeId> /tmp/ethora.env \
  | api POST compose.saveEnvironment -d @-
# domains
for d in "api 8080 api.$R /" "frontend 8080 app.$R /" "centrifugo 8000 app.$R /connection/websocket" \
         "xmpp 5280 xmpp.$R /ws" "xmpp 5280 xmpp.$R /bosh" "minio 9000 files.$R /"; do set -- $d
  api POST domain.create -d "{\"composeId\":\"<composeId>\",\"domainType\":\"compose\",\"serviceName\":\"$1\",\"port\":$2,\"host\":\"$3\",\"path\":\"$4\",\"https\":true,\"certificateType\":\"letsencrypt\",\"stripPath\":false}"
done
api POST compose.deploy -d '{"composeId":"<composeId>"}'
api GET "deployment.allByCompose?composeId=<composeId>"     # status and log path of each deployment
```

### Check

From the Dokploy server, the bundle's own end-to-end check, run against
Dokploy's copy of the compose project (`docker ps` shows the app name):

```bash
A=<app name>; D=/etc/dokploy/compose/$A/code/deploy/compose
docker compose -p $A --env-file $D/.env -f $D/docker-compose.yml --profile verify run --rm verify
```

It goes through the public URLs: certificates, web app, API docs, admin
login, licence state, a room created and a message sent over
`wss://xmpp.<root>/ws`, a file uploaded and read back from `files.<root>`.

### Update

Redeploy in Dokploy. Its compose command is `up -d --build`, which reuses
the images already on the host: turn on the service's "Pull images" option
(`pullImages` in the API, adds `--pull always`) or run `docker compose pull`
in the project directory first, so a redeploy picks up the release line's
latest images. The one-shot steps re-run and are idempotent. To move to a
newer line change the three `ETHORA_*_IMAGE` tags in the environment.

### Data

The named volumes are `<app name>_mongo`, `_mysql`, `_minio`, `_redis`
(see "Where the data is" in the bundle README; the backup commands apply
with these names). `/etc/dokploy/compose/<app name>/code/deploy/compose/.env`
holds every secret; Dokploy keeps a copy in its database. Deleting the
service in Dokploy removes the directory but not the volumes.

## Way 2: the template

The files in this directory are a Dokploy blueprint:

- `docker-compose.yml`: the bundle's compose file without the bundled Caddy,
  reading the scripts and templates from `../files/` (where Dokploy writes a
  template's mounts) instead of `./`.
- `template.toml`: the variables (`root_domain` from Dokploy's `${domain}`
  helper, every secret from `${password:N}`), the environment (every key of
  the bundle's `.env.example` except the per-host overrides and the proxy
  settings), the six domains of the table above, and the 7 scripts and 3
  templates as `[[config.mounts]]` file mounts (56 KB of the file's 61 KB).
- `meta.json` and `ethora.svg`: the catalogue entry.

`docker-compose.yml` and `template.toml` are generated: edit the bundle (or
`template.in.toml`) and run `./build-template.sh` (`--check` verifies the
checked-in files; the bundle test suite runs that). The mounts are TOML
literal strings, so backslashes in the scripts survive; Dokploy still
replaces its own helper names (`${domain}`, `${password}`, `${username}`,
...) inside mount content at deploy time, and the build refuses a script
that contains one.

Until it is in Dokploy's catalogue, use it in one of two ways:

- **Import**: project > Create Service > Compose (provider Raw), then
  Advanced > Import, paste the base64 of
  `{"compose": <docker-compose.yml>, "config": <template.toml>}` (both as
  strings; `python3 -c 'import json,sys,base64; print(base64.b64encode(json.dumps({"compose": open("docker-compose.yml").read(), "config": open("template.toml").read()}).encode()).decode())'`)
  and click Import. Dokploy replaces the service's compose file, environment,
  mounts and domains with the template's.
- **Catalogue URL**: serve this directory as
  `<base url>/blueprints/ethora-core/` together with a `<base url>/meta.json`
  that lists it (the array `build-scripts/generate-meta.js` of the templates
  repository writes), then Create Service > Template with that base URL, or
  `POST /api/compose.deployTemplate` with
  `{"environmentId": ..., "id": "ethora-core", "baseUrl": "<base url>"}`.
  This is how the template was verified: the service it creates has the
  raw compose file, 24 environment lines, 10 mounts and 6 domains, and
  after the three steps below every `verify` check passed, with a way-1
  stack running on the same host.

Before the first deploy of the created service:

1. **Environment**: set `ADMIN_EMAIL` to your address (it is the admin
   login; the template puts `admin@<root domain>` there). `ADMIN_PASSWORD`
   is generated and shown in the same tab. To use your own domain instead
   of the generated `<name>-<hash>-<ip>.sslip.io` root, change `ROOT_DOMAIN`
   here and the six domain hosts together.
2. **Domains**: Dokploy creates a template's domains without TLS. Edit each
   of the six, turn HTTPS on and choose Let's Encrypt (`domain.update` with
   `"https": true, "certificateType": "letsencrypt"` in the API). The web
   app only works over https: its API, XMPP and file URLs are `https://`
   and `wss://`.
3. **Advanced**: turn Isolated Deployment on, for the reason given in way
   1 (a template cannot ask for it; `compose.update` with
   `"isolatedDeployment": true` in the API).
4. **Deploy**. Same log and `init` end state as way 1; the project
   directory is `/etc/dokploy/compose/<app name>/code` with the compose file
   at its top and the mounts under `../files/`.

Check it like way 1, with `docker compose -p <app name> --project-directory
/etc/dokploy/compose/<app name>/code --env-file .../code/.env -f
.../code/docker-compose.yml --profile verify run --rm verify`. Run this way
on Dokploy v0.30.8, every check passed.

### Submit the template

Fork `github.com/Dokploy/templates`, copy `docker-compose.yml`,
`template.toml`, `meta.json` and `ethora.svg` to `blueprints/ethora-core/`,
and open a pull request against its `canary` branch. The repository's
checks (`build-scripts/validate-docker-compose.ts`, `validate-template.ts`,
`generate-meta.js --check`) pass on these files with warnings only (the
shell `${...}` expansions inside the mounted scripts are reported as
unresolved variables, which is expected); every pull request gets a preview
catalogue URL that can be used as the base URL above. Do not add a root
`meta.json`; it is generated at build time.

## Known differences from the bundle's own proxy

- `api.<root>/metrics` is reachable (the Caddyfile answers 404 there).
  Dokploy has no per-path deny; use a Traefik middleware on the `api`
  domain if Prometheus metrics must stay private.
- `files.<root>`: Traefik passes the `Host` header through, which MinIO's
  presigned URLs need; uploads have no size limit at the proxy.
- A template's domains start without TLS (see above); way 1 sets them
  with Let's Encrypt directly.
- Compose service names are visible host-wide on `dokploy-network` unless
  the service is isolated (see way 1, step 1); the bundle's own proxy has
  no such neighbours.
