# Backup and restore

What to back up on an Ethora install, two ways to do it, and how to restore
onto the same host or a replacement. Written for the clean path layout
(source `~/ethora-install-shared`, target `~/ethora`, data `~/ethora-data`);
see the layout section of [`deploy/README.md`](../../deploy/README.md#how-an-install-is-laid-out)
if your install predates it.

## What holds state

| What | Where | Why it matters |
|---|---|---|
| MongoDB | `~/ethora-data/mongo` | apps, users, chats, agents, settings, license state. The one thing you cannot recreate. |
| MySQL | `~/ethora-data/mysql` | ejabberd: rooms, room membership, message archive, rosters |
| MinIO | `~/ethora-data/minio` | uploaded files, avatars, media, secure attachments |
| AI Postgres | Docker volume `deploy_ai_pgdata` | embeddings for the AI knowledge base. Rebuildable by re-indexing; slow. |
| Redis | `~/ethora-data/redis` | cache and queues. Safe to lose. |
| Push uploads | `~/ethora-data/push-uploads` (or `PUSH_UPLOADS_DIR`) | APNs certificates and keys uploaded through the admin panel |
| API uploads | `~/ethora-data/api-uploads` | image-mode uploads scratch space |
| Configuration | `~/ethora-install-shared/deploy/config/deploy.yml`, `~/ethora-install-shared/deploy/.deploy.env` | every secret the install runs with. Without `.deploy.env` a restore has different generated secrets and cannot open the databases. |
| TLS certificates | `/etc/letsencrypt` | reissued automatically on a fresh host; keep them only to avoid rate limits on a quick rebuild |

Everything else (`~/ethora`, `node_modules`, builds, rendered `.env` files)
is regenerated by `install.sh` from the source checkout and `deploy.yml`.

## Method 1: logical dumps while running (recommended, nightly)

No downtime. Consistent per database; the three databases are dumped one
after another, so a message written between the Mongo and MySQL dumps can
appear in one and not the other. Acceptable for a nightly backup.

```bash
cd ~/ethora-install-shared
sudo deploy/scripts/export-stateful-snapshots.sh --label nightly \
    --output-dir /home/ubuntu/backups/$(date -u +%Y%m%dT%H%M%SZ)
```

That writes, into the output directory:

- `mongo.archive` (`mongodump --archive` of the app database),
- `ejabberd_db.sql` (`mysqldump --single-transaction`),
- `ai_service_embeddings.dump` (`pg_dump`, when the AI service is enabled;
  add `--skip-ai-postgres` to leave it out),
- `export-manifest.env` (what was exported and from where).

Add the pieces the script does not cover:

```bash
B=/home/ubuntu/backups/<that directory>
sudo cp ~/ethora-install-shared/deploy/config/deploy.yml ~/ethora-install-shared/deploy/.deploy.env "$B/"
sudo tar -C ~/ethora-data -czf "$B/minio.tgz" minio push-uploads 2>/dev/null || sudo tar -C ~/ethora-data -czf "$B/minio.tgz" minio
sudo chmod 600 "$B"/.deploy.env "$B"/deploy.yml
```

MinIO stores objects as plain files under `~/ethora-data/minio/<bucket>/`,
so a tar of the directory while running is safe: an object is either fully
there or not yet visible. For large installs replace the tar with
`mc mirror` to an off-host bucket, see [MINIO_OBJECT_MIGRATION.md](MINIO_OBJECT_MIGRATION.md).

Copy the directory off the host. `deploy.yml` and `.deploy.env` contain
every secret, so encrypt at rest and restrict who can read the backup
store.

Cron example (runs at 03:10 UTC, keeps 14 days):

```cron
10 3 * * * root cd /home/ubuntu/ethora-install-shared && D=/home/ubuntu/backups/$(date -u +\%Y\%m\%dT\%H\%M\%SZ) && deploy/scripts/export-stateful-snapshots.sh --label nightly --output-dir "$D" >/var/log/ethora-backup.log 2>&1 && cp deploy/config/deploy.yml deploy/.deploy.env "$D/" && tar -C /home/ubuntu/ethora-data -czf "$D/minio.tgz" minio && find /home/ubuntu/backups -maxdepth 1 -mtime +14 -type d -exec rm -rf {} +
```

## Method 2: filesystem snapshot with the stack stopped (before upgrades, migrations)

Exact and fully consistent; needs a minute or two of downtime. Use it
before a release-line upgrade, a data migration you want to be able to
undo, or a move to another host.

```bash
cd ~/ethora-install-shared
set -a; source deploy/.deploy.env; set +a
pm2 stop all
docker compose -f deploy/docker-compose.enterprise.yml stop
docker compose -f deploy/docker-compose.ai.yml stop 2>/dev/null || true

sudo tar -C /home/ubuntu -czf /home/ubuntu/backups/ethora-data-$(date -u +%Y%m%dT%H%M%SZ).tgz ethora-data
docker run --rm -v deploy_ai_pgdata:/v -v /home/ubuntu/backups:/b alpine \
    tar -C /v -czf /b/ai-postgres-$(date -u +%Y%m%dT%H%M%SZ).tgz .
cp deploy/config/deploy.yml deploy/.deploy.env /home/ubuntu/backups/

docker compose -f deploy/docker-compose.enterprise.yml start
docker compose -f deploy/docker-compose.ai.yml start 2>/dev/null || true
pm2 start all
```

On a cloud host with volume snapshots (EBS, DigitalOcean volumes) the tar
can be replaced by a snapshot of the volume that holds `~/ethora-data`,
taken while the stack is stopped. Stopping is what makes it consistent.

## Restore onto the same host

Restoring replaces data. Take a fresh backup first if anything written
since the one you are restoring might matter.

**From a filesystem snapshot** (method 2): stop the stack as above, move
the current `~/ethora-data` aside, untar the snapshot into place, start the
stack. Ownership inside the tar is preserved by `sudo tar`. If you also
restore `.deploy.env`, do so before starting: the databases were
initialised with the passwords in it.

**From logical dumps** (method 1), with the stack running:

```bash
cd ~/ethora-install-shared
set -a; source deploy/.deploy.env; set +a
B=/home/ubuntu/backups/<directory>
C="docker compose -f deploy/docker-compose.enterprise.yml"

pm2 stop backend backend-jobs backend-bc-worker ai-service push push-worker 2>/dev/null

$C exec -T mongo mongorestore --archive --drop --nsInclude "${MONGO_DB}.*" < "$B/mongo.archive"
$C exec -T mysql mysql -uroot -p"${MYSQL_ROOT_PASSWORD}" ejabberd_db < "$B/ejabberd_db.sql"
sudo tar -C ~/ethora-data -xzf "$B/minio.tgz"
if [ -f "$B/ai_service_embeddings.dump" ]; then
  docker compose -f deploy/docker-compose.ai.yml exec -T ai-postgres \
    pg_restore -U "${AI_POSTGRES_USER}" -d "${AI_POSTGRES_DB}" --clean --if-exists < "$B/ai_service_embeddings.dump"
fi

$C restart xmpp
pm2 start all
deploy/scripts/health-check.sh
```

Restart ejabberd after the MySQL import so it drops cached room state.
MinIO picks up files as soon as they are on disk.

## Restore onto a new host (disaster recovery, host move)

1. Install the same release line on the new host with the backed-up
   `deploy.yml` (same domains, or update `domains:` if they change) and
   start from the backed-up `.deploy.env`:
   ```bash
   git clone -b <line> git@github.com:dappros/ethora-install-shared.git ~/ethora-install-shared
   cp deploy.yml ~/ethora-install-shared/deploy/config/deploy.yml
   cp .deploy.env ~/ethora-install-shared/deploy/.deploy.env
   cd ~/ethora-install-shared && sudo deploy/scripts/install.sh --yes
   ```
   Restoring `.deploy.env` first means the databases are created with the
   old passwords and every secret (JWT signing key, XMPP secret, Centrifugo
   key) matches the data. Keep both files at mode 600.
2. Restore the data with either method above.
3. Point DNS at the new host. Certificates for the same names are reissued
   by the installer; if you moved `/etc/letsencrypt` as well, they are
   reused.
4. If the domains changed, the stored URLs inside MongoDB (logos, media
   paths, assistant prompts, room JIDs) need rewriting. That is the
   [stateful snapshot migration](STATEFUL_SNAPSHOT_MIGRATION.md) runbook;
   same-domain restores do not need it.

## Verify a backup

Do this at least once per install, and after changing the backup job:

```bash
B=/home/ubuntu/backups/<directory>
ls -la "$B"                                   # every file present, sizes plausible
docker run --rm -v "$B":/b mongo:6 sh -c 'mongorestore --archive=/b/mongo.archive --dryRun 2>&1 | tail -3'
head -c 300 "$B/ejabberd_db.sql"              # a mysqldump header, not an error
tar -tzf "$B/minio.tgz" | head               # bucket directories listed
```

The real test is a restore onto a scratch host. Rehearse it before you
need it.

## Retention

Keep at least: 7 daily, 4 weekly, and the pre-upgrade snapshot of each
release-line upgrade until the next one has soaked. Mongo and MinIO
dominate the size; MySQL (message archive) grows with chat volume.
